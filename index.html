Git & GitHub: guia de referência

Versionar é guardar o histórico de cada mudança do projeto, com quem mudou, quando e por quê, e poder voltar a qualquer ponto. Este guia cobre o essencial para começar: conceitos, as áreas por onde um arquivo passa, branches, pull requests e os comandos do dia a dia.

Conceitos

Git não é GitHub

Git

Programa instalado no seu computador que controla versões. Funciona 100% offline.

  • Grava “fotos” do projeto (commits)
  • Permite criar linhas paralelas de trabalho (branches)
  • Junta essas linhas depois (merge)

GitHub

Site que hospeda repositórios Git na nuvem e adiciona colaboração por cima.

  • Backup remoto do repositório
  • Pull requests, revisão de código, issues
  • Automação (GitHub Actions)
Analogia

Git é o “Controle de Alterações” do Word, só que para a pasta inteira do projeto e sem limite de histórico. GitHub é o Google Drive onde essa pasta com histórico fica guardada e compartilhada com o time.

GitHub: colaboração e compartilhamento

Os três recursos do GitHub que você vai usar desde o começo:

Repositórios

Guardam o projeto online e permitem que outras pessoas acessem e colaborem.

Pode ser público (qualquer um vê) ou privado (só quem você convidar). Projetos de cliente: sempre privado.

Pull requests

Pedido para integrar mudanças ao projeto principal, com espaço para revisão e aprovação antes do merge.

Fluxo completo na seção Pull request.

Issues

Lista de tarefas do projeto: registra bugs e melhorias, define responsável e acompanha o andamento.

Escrever fixes #12 na descrição do PR fecha a issue 12 automaticamente no merge.

Benefícios de usar Git e GitHub

Organização

Fim do Relatorio_v2_final_AGORA_VAI.pbix: um arquivo só, com todas as versões no histórico.

Cada versão tem data, autor e mensagem explicando o que mudou.

Colaboração

Várias pessoas trabalham no mesmo projeto ao mesmo tempo, cada uma na sua branch, e tudo fica rastreável.

Dá para saber quem alterou cada linha e por quê.

Segurança

O histórico continua salvo no GitHub mesmo se o seu computador quebrar ou for perdido.

Vale só para o que já foi enviado com git push. Commit sem push existe apenas no seu PC.

Pré-requisitos

Dois programas: o VS Code, onde você edita os arquivos e digita os comandos, e o Git, que faz o versionamento. Instale nessa ordem: o instalador do Git oferece o VS Code como editor padrão quando ele já está instalado.

Visual Studio Code

Download: code.visualstudio.com. Use o instalador para Windows (User Installer, x64).

Durante a instalação, na tela Select Additional Tasks, marque:

  • Add “Open with Code” action to Windows Explorer file context menu e o mesmo para directory: permite clicar com o botão direito numa pasta e abrir no VS Code.
  • Add to PATH (já vem marcado): é o que faz o comando code funcionar no terminal, inclusive o core.editor "code --wait" do Git.

Git

Página oficial de download: git-scm.com/install/windows. Os instaladores são publicados pelo projeto Git for Windows no repositório git-for-windows/git do GitHub.

Na página, em Other Git for Windows downloads, baixe Standalone Installer → Git for Windows/x64 Setup. A página sempre mostra a versão mais recente: use a que estiver lá.

Durante a instalação

Pode avançar com os padrões, mudando só duas telas:

  • Choosing the default editor: troque o Vim por Visual Studio Code (a opção só fica disponível com o VS Code já instalado). Vim confunde quem está começando.
  • Adjusting the name of the initial branch: marque Override the default branch name e deixe main, o mesmo padrão do GitHub.

As 4 áreas por onde um arquivo passa

Todo comando Git move mudanças entre estas áreas. Entendendo o diagrama, os comandos deixam de ser decoreba.

Por que existe a Staging Area? Porque você nem sempre quer gravar tudo que mudou. Imagine que alterou 3 medidas e um tema visual: dá para fazer git add só das medidas, commitar com a mensagem “otimiza medidas de vendas”, e depois commitar o tema separado. Histórico limpo, um assunto por commit.

Pegadinha comum

git commit não manda nada para o GitHub. O commit fica só no seu PC até você rodar git push. Se o HD queimar antes do push, o commit se perde.

Branches e merge

A main é a linha principal: a versão que está valendo, em produção. Uma branch é um desvio paralelo onde você trabalha sem mexer na main. Quando a mudança está pronta e revisada, ela volta para a main via merge.

E quando dá conflito?

Conflito acontece quando duas branches alteram a mesma linha do mesmo arquivo. O Git sabe juntar mudanças em linhas diferentes sozinho; na mesma linha, ele não tem como saber qual versão vale e para o merge esperando a sua decisão.

Exemplo em projeto PBIP: a medida Venda Líquida, no arquivo _Medidas.tmdl, foi corrigida por duas pessoas, cada uma em sua branch, de jeitos diferentes.

Como resolver. Abra o arquivo no VS Code. Acima do trecho aparecem quatro opções:

BotãoResultado
Accept Current ChangeFica a versão da main: SUM( ft_vendas[vl_venda_liquido] )
Accept Incoming ChangeFica a versão da dax-b: bruto menos desconto
Accept Both ChangesFicam as duas linhas. Aqui seria erro: duas medidas com o mesmo nome
Compare ChangesAbre as duas versões lado a lado, sem resolver

Também dá para editar à mão: apague os marcadores <<<<<<<, ======= e >>>>>>> e deixe a linha correta. Depois, conclua o merge:

git add _Medidas.tmdl
git commit -m "merge: define cálculo da Venda Líquida"
# ou desista e volte ao estado anterior: git merge --abort
Quem decide é a regra de negócio, não o Git

As duas versões são DAX válido; a dúvida é qual representa a Venda Líquida para o cliente. Se vl_venda_liquido já vem com o desconto aplicado na origem, as duas dão o mesmo número e a primeira é mais simples. Se não vem, só a segunda está certa. Confirme com quem conhece a regra antes de escolher o botão.

Opções de merge no pull request

Ao concluir um PR, o botão verde do GitHub tem uma seta com três opções. Todas levam o conteúdo da branch para a main; a diferença é como o histórico da main fica desenhado. Exemplo: uma branch com 3 commits (D, E, F) criada a partir de B, enquanto a main recebeu C.

OpçãoImpacto na mainMensagem do commitQuando usar
Create a merge commitEntram todos os commits da branch + o commit M de junção. O grafo mostra a branch em paraleloAs originais + “Merge pull request #N”Quer registrar que houve uma branch e preservar cada commit
Squash and mergeOs commits da branch viram um só (S). Linha reta, um commit por PREditável na hora; vem do título do PRBranch com commits de rascunho (“ajuste”, “corrige typo”); padrão mais usado em PRs pequenos
Rebase and mergeOs commits entram como cópias (D′, E′, F′) depois de C. Linha reta, sem commit extraAs originais de cada commitCommits já bem escritos e organizados, que valem ser preservados um a um

Com 1 commit na branch, como no aviso “The 1 commit from this branch…”, Squash e Rebase dão praticamente o mesmo resultado: um commit novo em linha reta. O Merge commit acrescenta o M.

Depois de Squash ou Rebase, o git branch -d pode recusar

Os dois criam commits com hash novo, então o Git local não reconhece que o conteúdo da branch já está na main e responde “not fully merged”. Confirmado o merge no GitHub, faça git switch main, git pull e apague com git branch -D nome-da-branch.

Para padronizar no projeto, em Settings → General → Pull Requests do repositório é possível deixar marcadas só as opções que o time usa (Allow merge commits, Allow squash merging, Allow rebase merging).

Pull request: o fluxo completo

Pull request (PR) é um pedido formal no GitHub: “revisa minhas mudanças da branch X e, se estiver ok, junta na main”. É onde acontece a revisão de código e a discussão antes de algo entrar em produção.

É assim que um PR aparece no GitHub:

perf: troca coluna calculada por medida no fVendas #42

Open henrique-rabello quer fazer merge de 3 commits em main a partir de feature/nova-medida
1 aprovação de revisor
Sem conflitos com a branch base
Pull request × git pull

Nomes parecidos, coisas diferentes. git pull é um comando que baixa mudanças do GitHub. Pull request é um recurso do site para propor e revisar mudanças antes do merge.

Template de pull request

Template é um modelo que preenche automaticamente a descrição de todo pull request novo. Garante que cada entrega explique o que muda, por quê e como foi validada, deixa o Closes # pronto para vincular a issue e, com a tabela antes × depois, registra os ganhos de cada otimização.

Como usar: salve como .github/pull_request_template.md e faça commit na main. O PR não tem tela de escolha de modelo: com um arquivo único, ele é aplicado sempre. As caixas - [ ] viram checkboxes clicáveis, e a contagem de itens marcados aparece na lista de PRs.

Template Campos obrigatórios no PR (GitHub Actions)

O template em Markdown é texto livre: quem abre o PR pode apagar ou alterar as seções. Como o GitHub não tem campo obrigatório para PR, a solução é uma verificação automática que lê a descrição e falha se o template não foi seguido. Ela roda quando o PR é aberto, quando a descrição é editada e a cada push; se faltar algo, o PR mostra um X vermelho com a lista do que está pendente.

Regra verificadaFalha quando
O que muda / Por quêA seção foi removida ou ficou vazia
Issue relacionadaNão há Closes #N (ou fixes/resolves) com número
Tipo de mudançaNenhuma opção marcada
Como foi validadoNenhum passo numerado escrito
ChecklistSeção removida ou algum item sem marcar

.github/workflows/validar-pr.yml (commit na main):

name: Validar descrição do PR
on:
  pull_request:
    types: [opened, edited, synchronize, reopened]
permissions:
  contents: read
jobs:
  descricao:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/github-script@v7
        with:
          script: |
            const txt = (context.payload.pull_request.body || '')
              .replace(/\r\n/g, '\n')
              .replace(/<!--[\s\S]*?-->/g, '');
            const secoes = {};
            txt.split(/^##\s+/m).slice(1).forEach(b => {
              const i = b.indexOf('\n');
              secoes[b.slice(0, i).trim()] = b.slice(i + 1);
            });
            const erros = [];
            for (const nome of ['O que muda', 'Por quê']) {
              if (!(nome in secoes)) erros.push(`Seção "${nome}" foi removida`);
              else if (secoes[nome].trim().length < 15) erros.push(`Seção "${nome}" está vazia`);
            }
            if (!/^(close[sd]?|fix(e[sd])?|resolve[sd]?)\s+(\S+\/\S+)?#\d+/im.test(secoes['Issue relacionada'] || ''))
              erros.push('Falta "Closes #N" com o número da issue');
            if (!/- \[x\]/i.test(secoes['Tipo de mudança'] || ''))
              erros.push('Marque ao menos um "Tipo de mudança"');
            if (!/^\s*\d+\.[ \t]+\S+/m.test(secoes['Como foi validado'] || ''))
              erros.push('Descreva ao menos um passo em "Como foi validado"');
            const check = secoes['Checklist'];
            if (check === undefined) erros.push('Seção "Checklist" foi removida');
            else if (/- \[ \]/.test(check)) erros.push('Há itens do "Checklist" sem marcar');
            if (erros.length) core.setFailed('Descrição do PR incompleta:\n- ' + erros.join('\n- '));

Para o X vermelho bloquear o merge, crie uma regra para a main em Settings → Rules → Rulesets com Require status checks to pass (escolha a verificação descricao) e Require a pull request before merging com aprovação obrigatória. Assim, o seu Request changes como revisor também trava o merge.

Regras de bloqueio dependem do plano

Em repositório privado, as regras de proteção de branch exigem GitHub Pro ou Team; na conta gratuita, só valem em repositórios públicos. Sem elas, a verificação continua mostrando o X vermelho como alerta, mas não bloqueia o botão de merge. E nenhuma automação avalia a qualidade do texto: ela garante a forma, a revisão garante o conteúdo.

Issues

Issue é um registro de tarefa dentro do repositório no GitHub: um bug, uma melhoria, uma dúvida. Cada uma ganha um número (#12), um título, uma descrição, um responsável e etiquetas, e guarda toda a conversa sobre o assunto. É a lista de pendências do projeto, ligada diretamente ao código.

CampoPara que serve
Título e descriçãoO que precisa ser feito ou corrigido, em Markdown
AssigneesQuem é responsável pela tarefa
LabelsEtiquetas de tipo e área: bug, enhancement, documentation, question (padrões do GitHub) e as que você criar, como dax, power-query, performance
MilestoneAgrupa issues de uma entrega: “Sprint 3”, “Versão 1.5”
DevelopmentMostra a branch e o pull request que resolvem a issue

Do problema ao merge

  1. Abrir a issue: aba Issues → New issue. Ela recebe um número, por exemplo #12.
  2. Criar a branch com o número: git switch -c fix/12-ytd-filtro-ano. Fica fácil saber a que tarefa a branch pertence.
  3. Citar a issue nos commits: rodapé Refs: #12. O commit aparece dentro da issue no GitHub.
  4. Abrir o PR com Closes #12 na descrição. O GitHub liga o PR à issue.
  5. Merge do PR na main: a issue #12 é fechada automaticamente.

Palavras que fecham a issue no merge: close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved, seguidas do número. Só funcionam quando o PR entra na branch padrão (a main).

Templates de issue

Templates são modelos que já abrem preenchidos no campo da issue. Servem para padronizar os chamados e garantir que quem abre informe o mínimo para o problema ser entendido sem ida e volta: passos para reproduzir, esperado × atual, onde ocorre, evidências.

Como usar: salve cada arquivo na pasta .github/ISSUE_TEMPLATE/ do repositório e faça commit na main. A partir daí, o botão New issue mostra uma tela de escolha com um cartão para cada modelo. O bloco entre --- no topo configura o cartão: nome (name), descrição (about), título inicial (title), label aplicada sozinha (labels) e responsável (assignees). Os comentários <!-- --> orientam o preenchimento e não aparecem na issue publicada.

Issue × pull request

A issue descreve o problema (o quê e por quê); o pull request entrega a solução (o código). Uma issue pode ser resolvida por um ou mais PRs, e o Closes #12 amarra os dois.

Templates de issue com campos obrigatórios (YAML)

Para tornar campos obrigatórios na issue, troque os templates .md por formulários .yml na mesma pasta .github/ISSUE_TEMPLATE/. Em vez de um texto livre, o GitHub mostra um campo para cada seção, e os que têm required: true impedem o envio enquanto estiverem vazios. Os dois arquivos abaixo têm as mesmas seções dos templates em Markdown.

Tipo de campoUso
textareaTexto longo; aceita prints arrastados. value já deixa um texto inicial
inputTexto de uma linha, como a versão do Power BI Desktop
dropdownLista de opções fixas, como Desktop, Serviço ou App
validations: required: trueTorna o campo obrigatório

Projects

O GitHub Projects é o quadro de planejamento do GitHub. Ele reúne issues e pull requests, de um ou de vários repositórios, e mostra tudo como tabela, quadro kanban ou roadmap (linha do tempo). Cada card é uma issue ou um PR de verdade: mudou na issue, muda no quadro.

Objetivo principal: dar uma visão única de o que está sendo feito, por quem e em que etapa, ao lado do código. Se a issue é o chamado, o project é o painel de chamados do time.

Criar e usar

  1. Criar: no seu perfil (ou na organização), aba Projects → New project → escolha o template.
  2. Vincular ao repositório: no repositório, aba Projects → Link a project. O projeto passa a aparecer ali.
  3. Adicionar issues: no quadro, + Add item e digite # para buscar a issue; ou, na própria issue, campo Projects na barra lateral.

GitHub Actions

O GitHub Actions é a ferramenta de automação integrada ao GitHub. Ele executa tarefas sozinho quando algo acontece no repositório (um push, um pull request, um horário agendado) e é com ele que se montam os pipelines de CI/CD. A verificação da descrição do PR da subseção 5.2 é um workflow do Actions.

CI e CD

CD · Entrega/Implantação ContínuaPublica a versão aprovada automaticamente num servidor, aplicação ou ambienteDepois do merge na mainPublicar o modelo e o relatório no workspace de homologação ou produção

Pipeline: do evento à entrega

Um pipeline é uma sequência de etapas automatizadas, disparada por um evento do repositório. As quatro etapas clássicas:

Anatomia de um workflow

Os workflows são arquivos YAML na pasta .github/workflows/. Cada arquivo descreve quando a automação roda, em qual sistema operacional e quais etapas executa.

TermoO que é
WorkflowO arquivo YAML que define a automação inteira
on:O evento que dispara o workflow: push, pull_request, schedule (horário, em cron), workflow_dispatch (botão Run workflow)
jobs:Tarefas independentes; por padrão rodam em paralelo
runs-on:O sistema do runner, a máquina temporária onde o job roda: ubuntu-latest, windows-latest, macos-latest
needs:Faz um job esperar outro terminar com sucesso
steps:Etapas sequenciais dentro de cada job
uses:Reaproveita uma ação pronta do GitHub ou da comunidade (Marketplace), como actions/checkout
run:Um comando de terminal executado pelo runner

Exemplo: CI para repositório PBIP

Workflow que roda em todo pull request e push na main: barra arquivos que não devem ir para o repositório (cache com dados, configurações locais, .pbix) e confere se os JSON do relatório estão válidos. Testado localmente.

.github/workflows/ci.yml

name: CI do projeto Power BI
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
jobs:
  verificar:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout do código
        uses: actions/checkout@v4

      - name: Bloquear arquivos que não devem ir para o repositório
        run: |
          proibidos=$(git ls-files '*.abf' '*localSettings.json' '*.pbix')
          if [ -n "$proibidos" ]; then
            echo "::error::Arquivos que não devem ir para o repositório:"
            echo "$proibidos"
            exit 1
          fi
          echo "Nenhum arquivo proibido."

      - name: Validar sintaxe dos JSON do relatório (PBIR)
        run: |
          find . -name '*.json' -not -path './.git/*' -print0 | xargs -0 -r -n1 python3 -m json.tool > /dev/null
          echo "JSON válidos."

Onde acompanhar: na aba Actions do repositório aparece cada execução, com o log de cada step e o botão Re-run jobs. No pull request, o resultado aparece como verificação (✓ ou ✗) acima do botão de merge.

São valores que o workflow usa, mas que não ficam escritos no código. Servem para duas coisas: manter dados sensíveis fora do repositório e permitir que o mesmo workflow rode com valores diferentes em cada ambiente.

Onde cadastrarSettings → Secrets and variables → Actions, abas Secrets e Variables → New repository secret / New repository variable

Níveis de cadastro

NívelAlcanceUso típico

Exemplo: job de publicação usando os dois, com valores do environment producao:

jobs:
  publicar:
    runs-on: ubuntu-latest
    environment: producao          # usa os secrets/variables do environment "producao"
    steps:
      - uses: actions/checkout@v4
      - name: Publicar no workspace
        env:
          WORKSPACE_ID: ${{ vars.WORKSPACE_ID }}    # variable: configuração visível
          TOKEN: ${{ secrets.FABRIC_TOKEN }}        # secret: valor oculto, *** no log
        run: ./publicar.sh

A forma recomendada é passar o secret por env:, como acima, em vez de escrevê-lo direto no comando do run:.

Caso Power BI: token de API no Power Query

No formato PBIP, o Power Query é salvo como texto: parâmetros em .SemanticModel/definition/expressions.tmdl e o M das consultas em tables/*.tmdl. Um token guardado num parâmetro ou escrito no M entra no Git a cada commit. Para conferir se isso já aconteceu, pesquise um trecho do token:

git log --oneline -S "trecho-do-token"   # commits que adicionaram ou removeram o texto
git grep "trecho-do-token"               # procura na versão atual dos arquivos

Na publicação, o padrão é versionar um valor falso e deixar o workflow aplicar o real:

O melhor caminho, porém, é tirar o token do Power Query:

AbordagemComo funcionaOnde o token fica
Credencial “Web API”Web.Contents(url, [ApiKeyName = "api_key"]) informa só o nome do parâmetro; o valor é digitado nas credenciais da fonte de dados. Para APIs que aceitam a chave na URLArmazenamento de credenciais do Power BI
Conector personalizadoCriado com o Power Query SDK; cuida da autenticação, inclusive token em cabeçalho (Authorization: Bearer)Armazenamento de credenciais do Power BI

Cuidados com secrets

Nunca use echo com um secret: o mascaramento nos logs ajuda, mas não é garantia. Secret nunca vai em arquivo do repositório, nem no .yml. E se um token vazou, mesmo que por poucos minutos, a única correção segura é gerar um novo e invalidar o antigo.

Custos e limites

Em repositórios públicos, os runners padrão do GitHub são gratuitos. Em privados, o plano inclui uma cota mensal de minutos; o consumo aparece em Settings → Billing da conta. Workflows curtos como o de CI acima levam poucos segundos por execução.

Tags e Releases

Servem para marcar versões: “o que foi entregue ao cliente em 15/10 é a v1.1.0”. A tag é um recurso do Git, um nome fixo num commit. A release é um recurso do GitHub, construído em cima de uma tag: uma página com título, notas do que mudou e arquivos anexos.

Tag × release

TagRelease
De quem éDo Git; funciona até sem GitHubDo GitHub; só existe no site
O que éUm nome fixo para um commitUma página sobre uma tag, com título, notas e anexos
Onde se criaTerminal (git tag) ou siteSite (Releases → Draft a new release) ou automação
RelaçãoPode existir sozinhaSempre aponta para uma tag

A diferença para a branch: a branch é um marcador que anda a cada commit novo; a tag fica parada no mesmo commit para sempre.

Por que existem

MotivoNa prática
Marcar o que foi entregueMeses depois, você sabe exatamente qual código estava em produção em cada cliente
Voltar no tempo com segurançagit switch --detach v1.0.0 mostra o projeto como estava na entrega
Comparar versõesListar commits e arquivos alterados entre duas entregas
Comunicar o que mudouAs notas da release viram o “o que há de novo”; os perf: listados viram o relatório de ganhos daquela versão
Disparar automaçõesUm workflow com on: push: tags: ['v*'] publica em produção só quando uma versão é criada, separando “fiz merge” de “liberei versão”

Comandos de tag

git tag -a v1.1.0 -m "Entrega: medidas de margem e otimização do YTD"   # cria no commit atual
git tag                         # lista as tags
git show v1.1.0                 # detalhes da tag e do commit
git push origin v1.1.0          # envia a tag ao GitHub (o push normal não envia)
git push --tags                 # envia todas as tags

git switch --detach v1.1.0      # vê o projeto como estava na entrega (volte com git switch main)
git log --oneline v1.0.0..v1.1.0   # commits entre duas entregas
git diff v1.0.0 v1.1.0 --stat      # arquivos alterados entre elas

git tag -d v1.1.0               # apaga a tag local
git push origin --delete v1.1.0 # apaga a tag no GitHub

Prefira a tag anotada (-a), que guarda autor, data e mensagem. A tag “leve” (sem -a) é só um nome. O número segue o SemVer descrito em Boas práticas › Commits: fix sobe o PATCH, feat sobe o MINOR e breaking change sobe o MAJOR.

Criar uma release no GitHub

  1. No repositório, clique em Releases (barra lateral direita) → Draft a new release.
  2. Em Choose a tag, escolha uma tag existente ou digite uma nova (o GitHub cria no commit da main).
  3. Clique em Generate release notes: o GitHub monta a lista de PRs desde a release anterior. Ajuste o texto se quiser.
  4. Anexe arquivos, se fizer sentido, e clique em Publish release.
Anexos em projetos Power BI

Não anexe .pbix com dados nem exportações com informação de cliente: a release fica visível para todos com acesso ao repositório. Prefira documentação, um PDF do relatório ou o resultado de uma validação.

Automatizar o número da versão

Como a regra do SemVer é mecânica, ferramentas leem os commits no padrão Conventional Commits e calculam a próxima versão sozinhas.

FerramentaComo funciona
release-please (Action do Google)A cada merge na main, mantém aberto um PR de release com a versão calculada e o CHANGELOG.md atualizado. Quando você faz o merge desse PR, ele cria a tag e a release. Você decide quando lançar
semantic-releaseTotalmente automático: a cada push na main com feat ou fix, já cria a tag e a release
Generate release notes (nativo)Não calcula a versão, mas monta as notas a partir dos PRs. Bom para começar sem automação

Para consultoria, o release-please costuma ser o mais adequado: numeração e changelog saem sozinhos, mas liberar a versão para o cliente continua sendo uma decisão sua. Workflow mínimo:

.github/workflows/release-please.yml

name: release-please
on:
  push:
    branches: [main]
permissions:
  contents: write
  pull-requests: write
jobs:
  release-please:
    runs-on: ubuntu-latest
    steps:
      - uses: googleapis/release-please-action@v4
        with:
          release-type: simple

Antes de usar, marque em Settings → Actions → General → Workflow permissions a opção Allow GitHub Actions to create and approve pull requests; sem ela, a ação não consegue abrir o PR de release. O release-type: simple guarda a versão num arquivo version.txt, adequado para projetos que não são pacotes de código, como um PBIP.

Pré-requisito de qualquer automação

Seguir o Conventional Commits com disciplina. Commit fora do padrão (“ajuste local”) não conta para a versão nem aparece organizado no changelog. Com Squash and merge, é o título do PR que precisa estar no padrão.

git reset --hard HEAD~1        # desfaz o último commit E apaga as mudanças
git revert <hash>              # cria commit que desfaz outro (seguro após push)

Recuperar o que “sumiu” (reflog)

git reflog                       # lista tudo por onde o HEAD passou
git reflog show feature          # movimentos de uma branch específica
git show 'HEAD@{2}'              # o que havia 2 movimentos atrás
git reset --hard 'HEAD@{1}'      # desfaz um reset errado
git branch recuperada 438714a    # recria branch apagada pelo hash

# no PowerShell, HEAD@{n} precisa de aspas simples

Cherry-pick (copiar commits de outra branch)

git cherry-pick a1b2c3d            # copia um commit para a branch atual
git cherry-pick a1b2c3d e4f5g6h    # copia vários commits
git cherry-pick a1b2c3d^..e4f5g6h  # intervalo, do a1b2c3d ao e4f5g6h
git cherry-pick -n a1b2c3d         # aplica as mudanças sem commitar
git cherry-pick -x a1b2c3d         # anota na mensagem de onde o commit veio
git cherry-pick --continue         # segue depois de resolver um conflito
git cherry-pick --abort            # cancela e volta ao estado anterior

Quem alterou cada linha (blame)

git blame arquivo.tmdl            # commit, autor e data de cada linha
git blame -L 10,25 arquivo.tmdl   # só as linhas 10 a 25
git blame -w arquivo.tmdl         # ignora mudanças só de espaço
git blame -C arquivo.tmdl         # detecta linhas movidas de outros arquivos
git log -L 10,25:arquivo.tmdl     # todas as versões desse trecho

Achar o commit que quebrou algo (bisect)

git bisect start
git bisect bad              # o commit atual está com problema
git bisect good 305b52d     # este commit antigo estava bom
# o Git vai para o commit do meio: teste e responda
git bisect good             # aqui ainda funcionava
git bisect bad              # aqui já estava quebrado
# repita até "... is the first bad commit"
git bisect reset            # obrigatório: volta para a branch normal

git bisect run <script>     # automatiza os testes com um script

Atalhos (alias)

# cria apelidos para comandos longos (uma vez por máquina)
git config --global alias.lg "log --oneline --graph --all"
git config --global alias.st "status"
git config --global alias.sw "switch"
git config --global alias.br "branch"
git config --global alias.cm "commit -m"
git config --global alias.unstage "restore --staged"
git config --global alias.last "log -1 --stat"

# uso: o alias substitui o comando original
git lg                      # = git log --oneline --graph --all
git cm "feat: ..."          # = git commit -m "feat: ..."
git unstage arquivo.txt     # = git restore --staged arquivo.txt

# gerenciar
git config --global --get-regexp alias   # lista os aliases criados
git config --global --unset alias.lg     # remove um alias

Stash: a gaveta temporária

O git stash guarda as edições que ainda não estão prontas para commit, deixa a pasta limpa e permite retomar depois. Uso típico: você está no meio de uma alteração na feature e precisa trocar para a main às pressas, sem commitar trabalho pela metade.

ComandoO que faz
git stashGuarda as edições na gaveta e deixa a pasta como no último commit
git stash listMostra o que está na gaveta (stash@{0} é sempre o mais recente)
git stash applyDevolve as edições para a pasta e mantém uma cópia na gaveta
git stash popDevolve as edições e tira da gaveta
git stash dropApaga o item mais recente da gaveta sem aplicar

pop × apply: o pop devolve e esvazia aquele item; o apply devolve e mantém a cópia, útil para aplicar as mesmas edições em outra branch ou como segurança caso dê conflito.

git stash                # guarda o trabalho pela metade da feature
git switch main          # resolve o urgente na main
# ... corrige, commita ...
git switch feature
git stash pop            # retoma de onde parou
Arquivos novos ficam de fora

O stash só guarda arquivos versionados. Arquivos novos (U no VS Code) continuam na pasta, a menos que você use git stash -u.

checkout × switch

git checkout fazia coisas demais (trocar branch, criar branch, restaurar arquivo). Desde 2019 o Git separou essas funções em git switch e git restore. Os dois jeitos funcionam; prefira os novos, que são mais difíceis de usar errado.

Boas práticas

Commits: padrão Conventional Commits

Referência: conventionalcommits.org (v1.0.0). É uma convenção leve para mensagens de commit: dá estrutura ao histórico, deixa claro o tipo de cada mudança e permite gerar changelog e número de versão automaticamente.

Estrutura da mensagem

<tipo>[escopo opcional]: <descrição>

[corpo opcional]

[rodapé(s) opcional(is)]
ParteRegraExemplo
TipoObrigatório. Diz a natureza da mudança.feat, fix, perf
EscopoOpcional, entre parênteses. Diz a parte do projeto afetada.fix(dax):, feat(visual):
DescriçãoObrigatória, logo depois de : (dois-pontos e espaço). Resumo curto do que mudou.corrige YTD com filtro de data
CorpoOpcional, separado por uma linha em branco. Explica o porquê e o contexto.Antes/depois de uma otimização
RodapéOpcional, separado por uma linha em branco. Referências e avisos.Refs: #42, BREAKING CHANGE: ...

Mudança que quebra compatibilidade (breaking change)

Quando a mudança pode quebrar algo que depende do projeto (por exemplo, renomear uma medida usada por outros relatórios), sinalize de uma das duas formas: ! logo antes dos dois-pontos, ou um rodapé BREAKING CHANGE:, sempre em maiúsculas. Pode usar as duas juntas.

feat(modelo)!: renomeia medida Total Vendas para Receita Bruta

BREAKING CHANGE: relatórios conectados a este modelo precisam
trocar a referência para [Receita Bruta].

Marque a versão entregue ao cliente com uma tag: git tag v1.5.0 e git push origin v1.5.0.

Mensagem completa, com corpo e rodapé

perf(dax): troca FILTER(ALL) por KEEPFILTERS em Meta %

Página Visão Geral caiu de 4,2 s para 1,1 s no Performance Analyzer.
Resultados conferidos contra a versão anterior.

Refs: #42

No terminal, cada -m vira um parágrafo: git commit -m "perf(dax): troca FILTER(ALL) por KEEPFILTERS" -m "Página Visão Geral caiu de 4,2 s para 1,1 s.". Para mensagens maiores, rode só git commit e escreva no editor do VS Code.

Regras de escrita

  • Descrição curta, até uns 50 caracteres, sem ponto final.
  • Verbo no presente, dizendo o que o commit faz: “adiciona”, “corrige”, “remove”. Não “adicionei” nem “adicionando”.
  • Um assunto por commit. Se a descrição precisa de “e”, provavelmente são dois commits.
  • Escolha um idioma e use sempre o mesmo no projeto.
  • O corpo explica o porquê; o quê já está no diff.

Com perf: padronizado, git log --oneline --grep="perf" lista todas as otimizações do projeto, prontas para virar relatório de ganhos para o cliente.

O que evitar

Repositório em pasta do Google Drive ou OneDrive

A sincronização pode corromper a pasta .git quando o sync “briga” com o Git. Mantenha os repositórios numa pasta local (ex.: C:\repos\) e use o GitHub como backup. Guardar este guia no Drive não tem problema.

git reset --hard e git push --force em repositório compartilhado

git reset --hard apaga alterações sem volta, e git push --force sobrescreve o histórico do GitHub. Em repositório compartilhado, podem sumir com o trabalho de colegas. Para desfazer algo que já foi enviado com push, use git revert.

Regras para nomes de pastas e repositórios

  • Tudo minúsculo, palavras separadas por hífen: projeto-impressionador, não Projeto Impressionador.
  • Sem espaços, acentos, ç ou caracteres especiais (& # % ( )): exigem aspas no terminal e quebram URLs.
  • Cliente primeiro, assunto depois: acme-dashboard-vendas. Na lista, os projetos do mesmo cliente ficam juntos.
  • Nome da pasta local igual ao nome do repositório no GitHub.
  • Nomes curtos: projetos PBIP criam pastas profundas, e o Windows tem limite de 260 caracteres no caminho (o core.longpaths do item 11.1 contorna isso no Git).

Git + Power BI

Arquivo .pbix é binário: o Git até guarda, mas não consegue mostrar o que mudou nem resolver conflitos. A saída é salvar como Projeto do Power BI (.pbip), que quebra o relatório em arquivos de texto.

  • .SemanticModel/definition/*.tmdl: tabelas, medidas, relacionamentos em texto. Um diff mostra exatamente qual medida DAX mudou.
  • .Report/definition/ (formato PBIR): páginas e visuais em JSON, um arquivo por visual.
  • O Power BI Desktop já cria um .gitignore que exclui .pbi/localSettings.json e .pbi/cache.abf (cache com dados, que não deve ir para o repositório).
